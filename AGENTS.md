# Работа Codex в Text-classification

## Цель и документы

Это учебный ML/NLP mini-product: классификация финансовой тональности,
от исходных данных до inference. Пользователь должен понимать код и решения.
Объясняй по-русски, сохраняй English identifiers и названия API.

- `SPEC.md`: контракты, решения, ограничения и критерии приёмки.
- `PLAN.md`: небольшие исполнимые шаги, зависимости, статус и свидетельства проверки.
- `classification_overall.txt`, `classification_day01.txt`–`classification_day07.txt`
  и исходный `README.md`: материалы задания. Не переписывай их без необходимости.
- Явное указание пользователя имеет приоритет. При расхождении материалов используй
  согласованные решения SPEC; существенные новые расхождения объясни пользователю.

## Рабочий цикл

1. Проверь `git status --short`, diff, активный пункт PLAN и нужный раздел SPEC.
   Не перечитывай все материалы в каждом чате, если контекст уже известен.
2. Выполняй запрошенный пункт. Если запрошен целый день — выполни его подзадачи
   последовательно. Не добавляй функциональность следующих дней или побочные refactors.
3. Перед кодом кратко объясни цель, вход/выход, ML-концепцию и способ проверки.
   При длительной работе сообщай существенные находки и следующий шаг.
4. Держи переиспользуемую логику в `src/finnews_sentiment/`, проверки в `tests/`.
   Notebook вызывает эту логику, показывает данные и помогает экспериментировать.
5. После каждого законченного пункта обнови notebook текущего дня и PLAN.
   Отмечай пункт завершённым только с проверенным результатом и notebook checkpoint.
6. Проверь контракты, затем исполни notebook с чистого kernel сверху вниз.
   Разделяй offline tests, проверки реальных данных и выполнение notebook.
   Недоступную проверку называй прямо; не выдавай её за успешную.
7. В конце покажи результат, ограничения, `git diff --stat` (с учётом untracked files)
   и предложи один конкретный commit message на английском. Commit только по запросу.

## Архитектура и качество

- Простые функции и явные зависимости; не создавай framework, factory или agent
  orchestration без необходимости. Не запускай sub-agents без запроса пользователя.
- Используй `Path`, type annotations публичных функций, информативные ошибки.
  Не подавляй type errors через широкие `ignore`/`Any`; проверяй контракт данных.
- Не выполняй download, training или чтение NLTK resources при импорте модуля.
- Пути определяются относительно корня проекта, без личных абсолютных путей.
- Сохраняй raw data неизменными. Не удаляй строки, не меняй классы и не превращай
  пропуски в строку `"nan"` незаметно. Любое изменение сопровождай отчётом.
- Покрывай тестами содержательные границы: неверная схема, неизвестный класс,
  пропуски, пустые тексты, duplicate/conflicting labels, воспроизводимость.
  Для документов и простых обратимых правок отдельные тесты не нужны.
- Уважай существующие изменения. Не делай reset/clean, не перезаписывай результаты
  работающего notebook и не прерывай его kernel/process.

## Правила ML

- Классы всегда `negative`, `neutral`, `positive`; будущая числовая схема
  `0=negative`, `1=neutral`, `2=positive`. Двоичные соглашения других проектов не переносить.
- Разделяй raw inspection, preprocessing, feature fitting, training и evaluation.
- TF-IDF vocabulary/IDF и любые обучаемые transformations fit только на train;
  при CV — внутри `sklearn.pipeline.Pipeline` каждого fold.
- Настройки выбираются на validation/CV, held-out test используется для итоговой оценки.
  Не улучшай модель на основе ошибок test. Дубликаты текста не должны пересекать split.
- Сохраняй seed, порядок строк, источник, версию данных, параметры, версии библиотек
  и class order. Не обещай рост метрики заранее, не выдумывай measurements.
- Объясняй форму данных: DataFrame `(N, columns)`, TF-IDF `(N, vocabulary_size)`,
  predictions `(N,)`, confusion matrix `(3, 3)`. Интерпретируй macro F1 и дисбаланс.

## Notebook как учебный checkpoint

- На каждый день `notebooks/dayNN_*.ipynb`; на каждый пункт PLAN отдельный раздел:
  цель → краткая теория → вызов кода → вывод/график → интерпретация → самопроверка.
- Все переменные создаются выше места использования. Нет зависимости от истории kernel.
- Подключай `src/` явно до появления packaging. Проверяй работу из корня и `notebooks/`.
- Реальный датасет не заменяй synthetic fixture. Fixtures допустимы только в tests.
- Download — отдельная явная команда; повторное выполнение анализа работает offline.
- Сохраняй outputs законченных шагов. Если kernel execution ограничен окружением,
  сохрани notebook и укажи, что execution пока не подтверждён.

## Окружение и команды

В текущем checkout окружение называется `venv/`, не `.venv/`. Не пересоздавай его
и не обновляй все зависимости без причины. Runtime day01 отделён от будущего ML stack.

```bash
venv/bin/python scripts/check_types.py
venv/bin/python -m unittest discover -s tests -v
venv/bin/python -m compileall -q src tests
git diff --check
# Подготовка данных (network только при отсутствии локального архива):
PYTHONPATH=src venv/bin/python -m finnews_sentiment.data.prepare_phrasebank --download
# Открыть notebook:
venv/bin/jupyter notebook notebooks/day01_eda.ipynb
```

Исполнение notebook через nbconvert/nbclient требует запуска kernel; недоступность
локальных sockets в sandbox — ограничение проверки, а не повод менять production code.
Pyright и pandas-stubs закреплены в requirements-dev.txt. После каждого изменения
Python или code cells обязательно выполняй `venv/bin/python scripts/check_types.py`:
она проверяет src/tests/scripts и временно экспортированный код всех notebooks.
Обычная команда pyright не проверяет .ipynb. Не отмечай шаг завершённым при type errors;
исправляй контракт, не отключай диагностику. Pylance использует standard mode и src
из pyrightconfig.json/.vscode/settings.json. Будущие notebook magics требуют явной
поддержки в exporter, а не молчаливого удаления ячеек из проверки.
